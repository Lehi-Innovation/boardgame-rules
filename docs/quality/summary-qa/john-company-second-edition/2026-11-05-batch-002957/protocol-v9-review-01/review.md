# Independent generic V9 protocol/checker review

The V9 lookup contract is coherent: complete applicable attached operative text may supply a lookup answer without a second factual paraphrase. Each actual request must still be mapped and answered in the same entry, with governing qualifiers and referenced rules included. Concrete legal/numerical cases still require a resolved conclusion/calculation; attaching a general rule cannot repair a wrong conclusion. All same-entry substantive assertions remain subject to strict independent whole-entry grading. There is no semantic auto-grading mechanism or technical-format-based factual score cap.

**Disposition: no blocking defect found in the V9 lookup conversion itself.** The checker is a partial structural diagnostic, with the technical conformance gaps and inherited source preconditions below. Its success must not be treated as complete protocol compliance or factual correctness. No actual game/QA data were accessed, so this review cannot establish whether the actual frozen source meets those preconditions.

## Inputs and reproducibility

Only the V8/V9 generic protocol text and generic checker code were read. Exact copies, neutral fixture code/results, execution output, version diffs, read record and SHA-256 bindings are saved here. The initial combined display truncated; complete numbered protocol/V9 code reads and the V8/V9 diff recovered the generic content. No manifests, actual summary, question bank, reader output, grade, history or other task's review were read. No shared inputs were edited, no browser or agent contact was used, and no semantic router or factual grading code was added.

Run `python3 -B fixtures/neutral_protocol_probes.py` from this directory. The fixture harness writes only beneath its own `fixtures` directory. The neutral source has labels, tokens and trays; it contains no game facts. Tests intentionally characterize unsafe structural acceptances, so matching them is evidence of a limitation, not factual approval. `fixtures/neutral-results.json` contains each probe and full observed checker output. `evidence-manifest.json` binds saved artifacts to exact hashes and excludes itself to avoid recursive hashing.

## V8/V9 consistency

The source indexer, start/end marker functions and attachment constructor are AST-identical between V8 and V9. The per-entry boundary/hash/attachment/order/nonoverlap checking prefix is also AST-identical. The optional separate row/list/paragraph helper is not imported or embedded. The V9 code change is the version label, conversion of quote/paraphrase ledger checks to lookup-map checks, and updated limit descriptions.

V9 protocol lines 3, 27, 35, 37, 39, 41, 43 and 45 together require actual same-entry asked-fact coverage, manual relevance decisions, necessary external/ancestor conditions, exact complete units, minimal actual case resolutions, honest abstentions, and later independent grading. The lookup ledger no longer requires `fact_source_section` or `supported_fact_or_case_result`; the checker accepts absent/empty/null legacy fields and rejects nonempty duplicate assertions. This is consistent with avoiding factual paraphrase duplication. It rejects V8 quote-kind ledgers as the wrong V9 format. Existing field name `fact_quote_checks` now contains lookup-map diagnostics; the name is historical and does not prove a quote or a fact.

The checker requires a literal nonempty question phrase, typed selected-reference list, selected IDs and at least one reference for each lookup. Unsupported clauses require nonempty string text and may have no references. The latter establishes only an explicit string; whether it is an honest, precise abstention requires independent review. A string that guesses can still pass its structural check.

## Verified structural checks

Neutral fixtures demonstrate rejection of changed/cropped/trailing-whitespace-trimmed attachments, wrong hashes/offsets/kinds/headings, reversed attachment order, parent/child overlap, overlapping I/T leaf aliases, repeated IDs, duplicate marked or unmarked units in `answer`, unknown/dangling markers, nonliteral clause phrases, nontext/unselected/empty lookup references, nonempty legacy fact/source fields, blank/nontext unsupported text, nonobject entries, non-list answers and empty ledgers. Positive cases cover adjacent parent introduction plus child, exact subtree/intro boundaries including level-one closure, code-point offsets and UTF-8 string hashes, and distinct disjoint units with identical text. The tests do not infer relevance or governing meaning from any of those successes.

## Material technical gaps if used as a complete protocol validator

**T1 — Required JSON fields/types are not comprehensively checked (inherited).** Missing or non-array `case_conclusions`, invalid `support`, invalid `evidence`, absent `inputs_read`, floating-point integer metadata, extra full text in metadata and a duplicate complete unit in another answer field all pass. The required `Applicable summary text` label is also unchecked. These conflict with the protocol schema/format if checker success is presented as full compliance. They do not impair the narrower checked source slices. Add a separate explicit schema/format check or document that the reader/parent performs it. The checker cannot determine whether a concrete case requires a conclusion, but it can validate that the field is an array of strings.

**T2 — Bank completeness is a separate flag (inherited).** Empty or duplicated answer banks can have `all_structure_and_declared_source_spans_valid=true` while `exact_ordered_unique_ids=false`. Consumers must require both flags for every reader; the first is a per-existing-row aggregate and is vacuously true for an empty bank. CLI completion/exit status is not a validity verdict. No consumer was inspected or assumed in this review.

**T3 — The unsupported error wording overstates the check.** At V9 checker line 117, “requires a precise abstention” is implemented as nonempty string validation. Keep precision/honesty as an independent semantic duty; wording such as “requires nonempty abstention text; meaning not checked” would be more exact. This is a diagnostic precision issue, not gameplay correctness.

## Inherited source and encoding preconditions

**L1 — Selectable-unit coverage is restricted.** Only column-zero level-two through level-six recognized headings create selectable units. Level-one headings close units but their following body text, and any preamble before a selectable heading, can be uncovered. A neutral fixture containing global qualifiers there produces no unit containing them. If the actual source has governing material in such locations, the protocol's requirement to attach all governing rules cannot be satisfied through valid selected units alone. The parent must verify that source-format precondition independently; this review did not read the actual source. Source hierarchy completeness does not imply semantic governing-context completeness.

**L2 — Fenced syntax detection is partial.** The checker explicitly rejects uncontained fences starting after zero to three spaces and any reserved source marker. A valid blockquote-contained fence is not rejected. The lexer is deliberately narrow, and the protocol's broad fenced-code unsupported warning is stronger than this guard. Parent/source review must enforce the restricted grammar; passing `units` is not a universal Markdown support test. No claim is made that the actual source contains such syntax.

**L3 — Exactness is relative to the supplied Python string.** Direct `check_data` preserves raw Unicode/CRLF slices (including a CR in a CRLF heading) and hashes their UTF-8 encoding. `check` at lines 127–129 uses `Path.read_text()`, which normalizes CRLF to LF. A neutral raw-CRLF attachment therefore fails the wrapper's normalized recomputation. This behavior exists in V8 too. Declare a shared decoding/newline policy or preserve raw decoded newlines if exact frozen bytes are intended. Code-point offsets are neither byte offsets nor UTF-16 indices. No actual input encoding was inspected here.

## Independent grading remains necessary

The harness intentionally shows structural acceptance of an unsplit compound question, an omitted clause, unrelated selected text, a guessed unsupported string, wrong extra answer prose and contradictory case text. These are expected limits of a literal checker, **not** evidence that V9 permits them. Protocol requirements and later strict whole-entry grading must reject actual substantive omissions, wrong conclusions, unsupported guesses and contradictions. Every asked actor, condition, amount, destination, timing and exception must be supplied from that same entry; correct facts elsewhere cannot fill a gap.

A selected full parent subtree can omit external definitions; an introduction plus child can omit governing ancestors, siblings or global restrictions. Readers must locate those manually, include complete necessary units and apply them to the requested case. Structural success cannot certify the “smallest appropriate set,” honest unknown status, actual individual-clause split, complete reading, preservation of the first full draft or correctness of self-check reasoning. Those remain procedural/semantic checks under the protocol. No factual score, cap, actual-source compatibility verdict or adoption decision follows from this review.
