## Parser and exact command approval

The anchored regular expression admits only the complete two-statement form with `const r`, `await tools.exec_command`, fixed object key order, `cmd`, decimal `24000`, and `text(r.output)`, with both semicolons. It supports exactly one JSON double-quoted string or two such strings joined by one `+`. Either key can use its exact quoted spelling. Spaces, tabs, CR, LF, VT and FF are admitted between the designated tokens; required keyword separators prevent merged identifiers. This is deliberately smaller than JavaScript.

Only the captured JSON string tokens are passed to `json.loads`; their decoded values are joined and serialized into the original `literal_read_call` spelling. No JavaScript expression, shell program or string payload is evaluated. JSON escape variants can yield the same command value. Raw control characters, raw U+2028/U+2029, invalid escapes, single-quoted strings, templates, variables, calls, extra operators and third strings are rejected. Valid escaped surrogate pairs work; lone surrogates and pairs split across two literal tokens are conservatively rejected.

Recognition does not approve a command. The unchanged proof constructs the allowlist from its fixed `READ_SCRIPT`, its two approved paths, permitted mode and exact index. The normalized whole body must be an exact member. Shell whitespace, program text, path, mode and index are never normalized. For these valid Unicode command strings, equality preserves their UTF-8 bytes. Neutral tests exercised the real fixed `READ_SCRIPT` as inert text, two synthetic paths containing quotes, Unicode and shell-looking characters, both original literal formats, separately permitted modes, and unapproved command mutations. A separately preapproved metadata command remains approved because its complete body independently matches its own entry.

Comments, computed/prototype/duplicate/extra keys, getters, spreads, changed key order, alternative numeric spellings or budgets, extra arguments, altered identifiers, extra semicolons and extra statements/calls do not enter the new grammar. Code-looking text, shell syntax, interpolation markers and comment delimiters inside a JSON string stay literal data; they confer no approval.

## Wrapper and inherited limitations

`load_proposal_proof()` resolves its own file, takes its grandparent as the source root, verifies both embedded source hashes, imports the original literal-equivalent module, and installs the normalizer. Its original `ROOT` and the bounded helper's `ROOT` remained the permitted source directory. Both simulated source-hash mismatches were refused before import. Static inspection found only generic-source import work at load time; actual data access lives in the uncalled original proof functions.

These hashes bind source versions, not filesystem location, import environment, arbitrary Python callers, or concurrent file replacement between checking and importing. Relocation can change the original module's root even with identical source bytes. Lower-level loader/installer helpers remain callable, and the output-name wrapper is not an authorization or capability boundary. Ordinary Python importing can create bytecode cache files before source execution when bytecode writing is enabled; this review ran with `python3 -B`. The original import also sets the process-wide `sys.dont_write_bytecode` flag. These are ordinary import behaviors, not runtime-data certification or sandbox guarantees.

The wrapper applies the original `call_body` first. Consequently it inherits outer Unicode `strip()` behavior, not merely the parser's ASCII whitespace set. It also inherits the existing leading `// @exec:` line removal: arbitrary content on that first pragma line is ignored, and a pragma without a newline still raises `IndexError`. Those behaviors were explicitly tested. They are pre-existing exceptions and malformed-input limits, not a newly implemented general comment parser. Ordinary comments remain rejected.

The prospective `prove` API requires a keyword-only explicit basename ending in `-js-format-proposal-proof.json`. Invalid names were rejected, and argument forwarding was tested only with a stub. The unchanged original uses exclusive `open('x')`, preserving existing output files. The wrapper does not automatically add this proposal's hashes to the original proof result: any future comparison must separately bind these exact reviewed inputs and its fresh review. There is no command-line actual-proof entry point in the proposal. None of these facts authorizes use now.
