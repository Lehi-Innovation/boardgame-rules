## Privacy and operational limits

The original session parser selects tool-call/output payload fields from response items rather than copying the entire session or profile/instruction records. Saved proof artifacts can retain raw tool-call input code, the declared boundary input and post-boundary tool-call inputs. Those payloads are not automatically scrubbed, and field selection alone is not a guarantee about the text embedded inside them. This review has not inspected actual payloads. The root must honor the plan's local privacy restriction and narrow-projection/record-hash rule for new I/O audits, and avoid copying raw session/profile/instruction bodies. No external send, publication or shared-registry action is within scope.

Setting `sys.dont_write_bytecode=True` before importing the exact proposal addresses the prior ordinary-bytecode-cache caveat. It does not turn imports or the wrapper into a sandbox. Hashes are version binding; they do not make check-and-import atomic against concurrent source changes. Use the fixed reviewed locations, keep those source files stable during the local operation, and refuse hash/root discrepancies. Relocation, implementation changes, broader parameters, altered evidence handling or a changed plan require reassessment.

The inherited parser limitations remain: one or two static JSON strings in the narrow grammar, original outer Unicode stripping and leading `// @exec:` handling, malformed single-line pragma `IndexError`, exact canonical-JSON object semantics for outputs, and no general JavaScript equivalence or resource-exhaustion claim. The wrapper's unchanged result text alone does not describe or bind the normalization method; the separately named result and external adoption/plan/review/input/runtime bindings must do so.
